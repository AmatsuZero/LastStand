## 2. 假如你是一个项目的负责人，面对一个新需求你会如何判断以及决策 {#question-subjective-e13e2c7222bb}

### 题目要点

- 业务价值与需求背景明确 / 技术可行性与风险评估 / 资源与时间合理估算<br>
- 多方案设计与优劣比较 / 风险预判及缓解措施<br>
- 结合团队和业务做权衡决策 / 明确执行计划与责任 / 持续跟进与复盘优化<br>
- 沟通协调能力和风险管理能力是关键<br>
- 决策既考虑短期交付，也兼顾长期维护和团队承受能力

<details>
<summary>参考答案</summary>

### 考察点

- 评估候选人对需求分析和项目管理流程的理解<br>
- 探查其在技术可行性、资源评估、风险管理等方面的判断能力<br>
- 了解候选人如何在多方利益、时间与质量之间做权衡决策<br>
- 关注其沟通协调和方案落地的思路<br>

---

### 参考答案

#### 一、需求理解与评估

1. **明确需求背景和目标**<br>
   - 充分沟通业务方，理解需求的业务价值、核心目标和痛点<br>
   - 判断该需求是新增功能、优化还是技术债清理<br>

2. **技术可行性分析**<br>
   - 评估现有系统架构、技术栈对该需求的支持程度<br>
   - 识别技术难点和潜在风险，如性能、安全、兼容性等问题<br>

3. **资源与时间评估**<br>
   - 估算开发、测试、上线所需的人力、时间和成本<br>
   - 考虑团队现有工作负载，排期合理性<br>

#### 二、方案设计与风险控制

1. **设计多套实现方案**<br>
   - 比较不同方案的优劣，如技术复杂度、扩展性、维护成本<br>
   - 结合业务优先级和技术条件选择最优方案<br>

2. **风险预判与缓解**<br>
   - 识别潜在风险点，设计应对措施（如技术预研、灰度发布）<br>

#### 三、决策与执行

1. **结合业务战略和团队实际作出决策**<br>
   - 权衡需求价值与资源限制，明确是否优先推动或延期<br>
   - 与产品、设计、测试等多方协作，达成共识<br>

2. **推动方案落地**<br>
   - 制定详细开发计划，分解任务，明确负责人和时间节点<br>
   - 跟踪进展，快速解决过程中出现的问题<br>

3. **复盘与优化**<br>
   - 需求完成后组织复盘，总结经验，优化流程

- 制定针对性优化方案，优先解决影响最大的瓶颈<br>

#### 五、持续迭代与复盘

- 将监控和分析形成常态化流程，确保功能优化闭环<br>
- 定期复盘评估结果，总结经验教训<br>
- 结合业务目标调整优化策略，持续提升功能效果

## 5. 移动端兼容性处理是如何实现的呢 {#question-subjective-55b66f7f2ab2}

### 题目要点

- 多样化设备和浏览器差异导致兼容问题<br>
- 视口控制和响应式设计是基础<br>
- CSS前缀和PostCSS工具确保样式兼容<br>
- Babel与Polyfill保障JS语法和API支持<br>
- 功能降级保证核心体验<br>
- 多环境真机测试和远程调试<br>
- 性能优化助力兼容体验

<details>
<summary>参考答案</summary>

### 考察点

- 了解移动端兼容性问题的多样性及成因<br>
- 掌握主流兼容性处理技术和策略<br>
- 理解不同设备、操作系统、浏览器环境差异带来的挑战<br>
- 掌握解决方案的优缺点及适用场景<br>

---

### 参考答案

#### 一、移动端兼容性问题的成因

- 移动端设备种类繁多，屏幕尺寸、分辨率不一<br>
- 不同操作系统（iOS、Android）及版本差异<br>
- 各浏览器内核差异，如WebKit、Blink等，支持的标准和API不同<br>
- 网络环境复杂，性能表现差异大<br>
- 触控交互和硬件特性特殊，如手势、摄像头、陀螺仪等<br>

#### 二、常见的兼容性处理手段

1. **视口适配（Viewport）**<br>
   - 设置合理的 `&lt;meta name="viewport"&gt;` 标签，控制页面缩放和布局宽度<br>
   - 结合响应式设计，利用CSS媒体查询适配不同屏幕尺寸<br>

2. **CSS兼容性处理**<br>
   - 使用前缀（-webkit-、-moz-等）确保样式兼容<br>
   - 采用现代CSS特性同时兼容降级方案<br>
   - 利用PostCSS、Autoprefixer等工具自动添加兼容前缀<br>

3. **JavaScript兼容性处理**<br>
   - 通过 Polyfill 补充新标准API缺失支持<br>
   - 使用 Babel 转译ES6+语法，兼容低版本浏览器<br>
   - 运行时检测环境差异，动态加载对应代码<br>

4. **功能降级与优雅降级**<br>
   - 对不支持的特性提供替代方案或简化体验<br>
   - 确保核心功能可用，即使部分高级效果缺失<br>

5. **测试与调试**<br>
   - 在真机和模拟器上进行多环境测试<br>
   - 利用远程调试工具（如Chrome DevTools、Weinre）定位兼容问题<br>
   - 集成自动化测试，覆盖主流设备和浏览器<br>

6. **性能优化兼容**<br>
   - 适配不同网络环境，使用按需加载、资源压缩等技术<br>
   - 避免性能瓶颈导致兼容性表现差<br>

#### 三、项目中的应用场景及注意点

- 设计响应式布局，确保页面在手机、平板、不同分辨率设备上均正常展示<br>
- 处理iOS和Android差异，如输入法、滚动行为、事件响应差异<br>
- 关注浏览器私有API限制，如Safari的限制政策<br>
- 对第三方库或组件兼容性做充分验证<br>

#### 四、总结

移动端兼容性处理是一项系统工程，涉及视口适配、CSS和JS兼容策略、功能降级以及多环境测试。通过合理设计和工具链支持，能够最大限度地覆盖用户设备，提升体验一致性和稳定性。

</details>

## 6. 哪些浏览器会在图片兼容性上有问题呢 {#question-subjective-c1ee8b62ad7d}

### 题目要点

- WebP和AVIF是现代高效格式，但旧Safari和IE不支持<br>
- Safari对WebP支持从14版本开始，AVIF更晚<br>
- IE浏览器兼容性差，现代格式均不支持<br>
- SVG兼容性存在差异，需注意安全和复杂特性<br>
- 采用`<picture>`和格式回退方案保障兼容<br>
- 构建工具多格式自动转换，兼顾性能与兼容<br>
- 动态检测用户环境，选择合适图片格式

<details>
<summary>参考答案</summary>

### 考察点

- 了解不同浏览器对图片格式和特性的支持差异<br>
- 掌握常见图片格式（如WebP、AVIF、HEIC等）兼容性现状<br>
- 识别主流浏览器在图片加载和渲染方面的兼容问题<br>
- 能针对兼容性问题设计合适的处理方案<br>

---

### 参考答案

#### 一、常见图片格式及浏览器支持情况

| 图片格式 | 描述                   | 主要兼容问题及浏览器支持情况                          |
| -------- | ---------------------- | ---------------------------------------------------- |
| JPEG/PNG | 传统主流格式           | 广泛支持，兼容性好                                   |
| GIF      | 支持动画               | 支持较好，但色彩和压缩效率有限                       |
| WebP     | Google主导的现代格式   | Chrome、Firefox、Edge支持较好；Safari从14版本开始支持，旧版Safari不支持 |
| AVIF     | 新兴高压缩率格式       | Chrome 85+、Firefox 93+支持；Safari 16开始支持，较新且未广泛支持  |
| HEIC/HEIF| Apple设备常用格式      | 主要iOS/macOS支持，Windows和大多数浏览器不支持       |
| SVG      | 矢量图，兼容性好       | 需注意SVG安全问题和部分复杂特性浏览器支持差异       |

#### 二、具体浏览器兼容问题分析

1. **Safari（尤其旧版本）**<br>
   - 早期版本不支持WebP格式图片<br>
   - AVIF支持较晚，低版本完全不支持<br>
   - 对HEIC/HEIF格式支持较好，但非网页原生格式<br>
   - SVG部分高级特性兼容有限<br>

2. **IE浏览器（已停止维护，但部分企业仍用）**<br>
   - 不支持WebP、AVIF等现代格式<br>
   - SVG支持不完善，存在安全漏洞和渲染差异<br>

3. **部分安卓浏览器**<br>
   - 一些第三方或老版本浏览器对WebP兼容不完全<br>
   - 对SVG支持不稳定<br>

#### 三、兼容性处理方案

- **格式回退机制**<br>
  - 通过`<picture>`标签，结合`source`元素按浏览器能力加载对应格式图片<br>
  - 使用JS检测支持情况，动态切换图片资源<br>

- **构建工具自动转换**<br>
  - 利用构建工具（如webpack、vite）对图片进行多格式转换，生成兼容资源<br>

- **监测用户设备和浏览器版本**<br>
  - 根据用户环境调整图片格式策略，避免不支持格式加载失败<br>

- **合理选择图片格式**<br>
  - 关键内容优先保证主流格式兼容，增强用户体验

</details>

## 8. 有去了解过当前浏览器的内核分布，以及有多少种内核吗 {#question-subjective-90af48b8d8c3}

### 题目要点

- 浏览器内核是渲染和执行网页的核心组件<br>
- 主流内核主要有Blink、WebKit、Gecko、Trident、EdgeHTML<br>
- Blink占主导，WebKit是iOS/macOS唯一内核<br>
- 内核差异影响兼容性和功能表现<br>
- 针对不同内核做兼容测试和处理<br>
- 关注内核市场份额及技术发展动态

<details>
<summary>参考答案</summary>

### 考察点

- 理解浏览器内核的概念及其在浏览器中的作用<br>
- 掌握主流浏览器内核类型及其市场分布情况<br>
- 理解内核差异对前端开发和兼容性的影响<br>
- 能根据内核特点制定相应的开发和优化策略<br>

---

### 参考答案

#### 一、浏览器内核概念

- 浏览器内核（Rendering Engine / Layout Engine）负责解析网页内容，渲染页面，执行脚本等<br>
- 它是浏览器架构中最核心的组件，决定了页面渲染效果和性能表现<br>

#### 二、主流浏览器内核种类及特点

| 内核名称      | 代表浏览器              | 特点与现状                                         |
| ------------- | ----------------------- | ------------------------------------------------- |
| **Blink**     | Chrome、Edge（Chromium版）、Opera、Android WebView | 基于WebKit分支，开源、性能优异，市占率最高          |
| **WebKit**    | Safari、部分iOS浏览器    | 苹果主导开发，iOS平台强制使用，稳定兼容性好        |
| **Gecko**     | Firefox                 | Mozilla开发，强调开放与隐私，功能丰富但占比较小    |
| **Trident**   | 旧版Internet Explorer  | 微软老旧内核，兼容性差，已被Edge取代              |
| **EdgeHTML**  | 旧版Microsoft Edge      | 微软自研内核，现已弃用，转向Chromium内核          |

#### 三、当前内核市场分布（大致情况）

- Blink内核占据主导地位，尤其是在PC端和安卓端浏览器中<br>
- WebKit作为iOS和macOS的唯一浏览器内核，覆盖大量苹果设备用户<br>
- Gecko内核Firefox拥有一部分忠实用户，尤其重视隐私保护<br>
- Trident和EdgeHTML已经逐步被市场淘汰，使用者极少<br>

#### 四、内核差异对前端开发的影响

- 不同内核对CSS标准、JS引擎支持程度和API兼容性存在差异<br>
- 特殊行为和Bug需针对特定内核做兼容处理<br>

## 10. 介绍项目中的瀑布流组件是如何实现的 {#question-subjective-d3f0586f19e8}

### 题目要点

- 瀑布流通过分配元素到高度最短列实现均衡布局<br>
- JS控制列高数组，动态计算绝对定位实现最佳效果<br>
- CSS多列和Grid方案易用但控制力有限<br>
- 需处理图片异步加载和响应式布局<br>
- 性能优化、兼容性和用户体验是实现关键<br>
- 虚拟滚动等技术助力海量数据场景

<details>
<summary>参考答案</summary>

### 考察点

- 理解瀑布流布局的核心原理与实现方式<br>
- 掌握前端布局算法设计，特别是多列等高动态分布问题<br>
- 熟悉DOM操作、性能优化和响应式设计相关技巧<br>
- 能结合项目需求选择合适的实现方案并处理边界问题<br>

---

### 参考答案

#### 一、瀑布流布局原理

- 瀑布流是一种多列布局，动态分配不同高度的元素到各列，使整体视觉效果均衡<br>
- 目标是避免固定行高导致的空白，提升空间利用率和用户体验<br>
- 核心思路是将元素逐个放入当前高度最短的列中，保持各列高度差异最小<br>

#### 二、实现方式

1. **纯前端JavaScript实现**<br>
   - 获取容器宽度和列数<br>
   - 动态计算每列宽度<br>
   - 维护一个数组记录每列当前高度<br>
   - 遍历元素，找到高度最小列，将元素放入该列，并更新该列高度<br>
   - 设置元素的绝对定位(top, left)实现布局<br>

2. **CSS多列布局（column-count）**<br>
   - 利用CSS `column-count`快速实现简单瀑布流<br>
   - 缺点是元素顺序从上到下排列，无法精准控制列高度平衡<br>

3. **CSS Grid布局**<br>
   - 利用Grid布局实现基本多列排布<br>
   - 通过`grid-auto-flow: dense`实现部分填充<br>
   - 但Grid对高度不均衡的元素支持有限，需配合JS调整<br>

#### 三、项目中具体实现细节

- 在数据加载后，动态计算每个瀑布块元素的实际高度<br>
- 通过JavaScript将元素依次放入当前高度最小的列<br>
- 监听窗口resize事件，重新计算列数和布局，实现响应式支持<br>
- 对图片等异步加载资源，使用监听事件或占位符确保布局稳定<br>
- 通过requestAnimationFrame或节流防抖优化重排频率，减少性能开销<br>

#### 四、优化点与注意事项

- **性能优化**：避免大量DOM重排，批量更新位置；使用虚拟滚动技术处理海量数据<br>
- **响应式支持**：根据屏幕宽度调整列数和元素宽度<br>
- **图片加载处理**：防止图片加载导致高度变化破坏布局，使用占位符或图片懒加载<br>
- **兼容性考虑**：兼容不同浏览器对定位和尺寸计算的差异<br>
- **SEO与可访问性**：保证瀑布流结构语义清晰，方便搜索引擎爬取和辅助设备访问

## 11. 还有什么别的方式能实现瀑布流呢 {#question-subjective-724798ef1f6d}

### 题目要点

* CSS多列布局简单易用，但元素顺序不可控
* CSS Grid适合固定高度或等高布局，动态高度表现一般
* JS绝对定位方案最灵活，能实现最佳视觉效果
* 虚拟列表适合大规模数据，性能优势明显
* 结合业务需求和项目复杂度选择实现方式
* 可考虑使用第三方库提升开发效率

<details>
<summary>参考答案</summary>

### 考察点

- 掌握多种瀑布流实现方案，理解它们的优缺点和适用场景<br>
- 理解纯CSS、纯JS、混合方案及第三方库的不同实现思路<br>
- 能根据项目需求选择合适方案，权衡开发成本和性能<br>

---

### 参考答案

#### 一、CSS多列布局（CSS Columns）

- 利用CSS属性`column-count`或`column-width`实现多列分布<br>
- 元素自动按列流式排列，省去手动计算和定位<br>
- 优点：实现简单，性能开销小，响应式支持较好<br>
- 缺点：元素排列顺序是按列流式排列，无法保证元素顺序的语义一致性或完全均衡的列高<br>

```css
.container {
  column-count: 4;
  column-gap: 16px;
}
.item {
  break-inside: avoid; /* 避免元素被拆分 */
  margin-bottom: 16px;
}
````

#### 二、CSS Grid布局

* 使用Grid的多列布局和自动排列功能
* 通过`grid-auto-flow: dense;`尝试填充空隙
* 优点：更灵活的布局能力，可控制元素顺序
* 缺点：对于高度不一的元素，布局不够均衡，存在空白

#### 三、Flexbox结合JavaScript

* 通过Flex布局进行列布局基础，结合JS动态分配元素
* 适合简单场景，灵活度高
* 需自行维护列高，做绝对定位或flex顺序调整

#### 四、纯JavaScript计算定位（常用）

* 维护列高数组，动态定位每个元素
* 完全控制布局，能实现高度均衡、顺序控制
* 实现复杂，需要关注性能和异步加载处理

#### 五、虚拟列表技术

* 结合瀑布流和虚拟滚动，只渲染可视区域元素
* 适合海量数据瀑布流，显著减少DOM节点
* 实现复杂，需解决滚动位置和元素高度动态计算

#### 六、第三方库与框架

* 使用成熟瀑布流库，如Masonry.js、Waterfall.js等
* 优点：快速集成，功能完善，兼容性好
* 缺点：体积较大，定制化有限

### 参考答案

#### 一、H5与移动端通信的基本概念

- H5页面运行在移动端浏览器或WebView内，和原生App环境是不同的执行上下文<br>
- 通信需要跨环境桥接，传递消息、数据和调用能力<br>
- 典型场景包括H5调用原生功能，原生通知H5事件<br>

#### 二、常见通信方式

1. **URL Scheme（协议拦截）**<br>
   - H5通过修改`window.location`或iframe跳转带有自定义协议的URL（如`myapp://action?param=xxx`）<br>
   - 原生拦截该URL并解析执行相应操作<br>
   - 优点：实现简单，兼容性好<br>
   - 缺点：只能单向通信，数据量有限，频繁跳转体验差<br>

2. **JavaScript Interface（JSBridge）**<br>
   - 通过原生提供的桥接接口，将JS方法映射到原生函数<br>
   - H5调用`window.Native.method(params)`，原生接收并处理<br>
   - 原生也可调用JS回调实现双向通信<br>
   - 优点：交互灵活，支持复杂数据传输<br>
   - 缺点：实现复杂，需维护多平台桥接代码<br>

3. **PostMessage机制（WebView专用）**<br>
   - 利用`window.postMessage` API实现跨环境异步通信<br>
   - 原生WebView提供监听接口捕获消息并响应<br>
   - 适用于iOS WKWebView和Android WebView<br>
   - 优点：安全、标准，支持双向通信<br>
   - 缺点：需保证协议设计安全，防止注入攻击<br>

4. **事件监听和回调**<br>
   - 结合JSBridge或postMessage，使用事件机制通知双方状态变化<br>
   - 便于管理复杂交互和异步回调<br>

#### 三、实际项目中的应用示例

- 用户点击H5按钮调用原生相机功能：通过JSBridge调用原生API<br>
- 原生扫码结果通过postMessage传给H5，H5页面更新UI<br>
- 通过URL Scheme唤起App某个页面或功能<br>
- 结合Hybrid框架（如Weex、React Native WebView模块）统一通信接口<br>

#### 四、需要注意的问题

- **安全性**：防止恶意注入或非法调用，校验传入参数和来源<br>
- **性能**：避免频繁通信导致卡顿，合理设计调用频率<br>
- **兼容性**：处理不同平台（iOS/Android）桥接差异<br>
- **异步处理**：通信多数为异步，需设计完善的回调或Promise机制<br>
- **版本维护**：原生和H5接口需同步升级，保持兼容

   - 通常依赖Intl API或第三方库（如`intl-messageformat`）实现格式化<br>

5. **占位符和变量替换**<br>
   - 支持模板字符串或变量插入，避免重复定义同一文本<br>
   - 支持复杂复数规则处理（如英文的单复数形式）<br>

#### 三、常用工具与库

- **vue-i18n / react-intl / i18next** 等，封装语言管理、切换和格式化API<br>
- 支持异步加载语言包，减少首屏负载<br>
- 支持语言检测和回退策略<br>

## 15. 算法题： {#question-subjective-d1bfdc40ef9c}

- （1）求数组深度（递归和迭代都要写）
- （2）实现Promise.half方法（后面要求能失败重试）

### 题目要点

递归与显式栈计算嵌套数组深度；明确空数组的深度定义；为 Promise 扩展定义任务工厂、并发上限、失败重试和最终错误传播。

<details>
<summary>参考答案</summary>

数组深度可以递归计算，也可以用显式栈迭代。下面约定非数组深度为 0、空数组深度为 1：

```js
function arrayDepth(value) {
  if (!Array.isArray(value)) return 0;
  return value.length === 0
    ? 1
    : 1 + Math.max(...value.map(arrayDepth));
}

function arrayDepthIterative(value) {
  if (!Array.isArray(value)) return 0;
  let max = 1;
  const stack = [{ value, depth: 1 }];
  while (stack.length) {
    const current = stack.pop();
    max = Math.max(max, current.depth);
    for (const item of current.value) {
      if (Array.isArray(item)) stack.push({ value: item, depth: current.depth + 1 });
    }
  }
  return max;
}
```

`Promise.half` 不是标准 API，编码前应先与面试官确认它表示“半数并发”还是其他语义。若要求限制并发并支持失败重试，入参应使用可重新执行的任务工厂，而不是已经开始的 Promise；实现时维护待执行队列和运行计数，单任务失败后在重试次数内重新入队，超过次数则拒绝最终 Promise，并按约定决定是否继续其他任务。

</details>
