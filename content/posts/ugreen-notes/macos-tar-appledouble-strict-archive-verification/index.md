## 现象

清理研究产物前，先把展开的 JSON/HTML 报告归档，再逐文件核对大小和 SHA256。
源文件清单没有 `._reports`，但读取 macOS 系统 `tar` 生成的归档时出现了类似
`evidence/._reports` 的额外条目。严格校验按预期失败；此时尚未删除任何源文件。

## 已验证成因

实测工具为 `bsdtar 3.5.3`、`libarchive 3.7.4`。本机 `man tar` 的
`--mac-metadata` 说明：创建归档时，默认通过 `copyfile(3)` 把扩展 ACL 和扩展属性
保存为 AppleDouble 数据。因此，归档中合成的 `._*` 条目不一定是源目录中的文件，
不能直接据此认定原始报告损坏或归档器丢失正文。

## 有效恢复

本例只要求保存可重新读取的报告文件内容、普通权限和目录结构，不要求保留资源叉、
扩展属性或扩展 ACL。仅给此次归档进程关闭 macOS 元数据打包：

```bash
COPYFILE_DISABLE=1 tar --no-mac-metadata -cf evidence.tar reports/
```

先对带有元数据的实际目录做最小归档探针，确认不再出现合成条目；随后重做完整归档。
在一次真实验证中，归档内 8,734 个文件的路径、大小和 SHA256 全部与源清单相同。
只有完整验证通过后，才删除源目录中的展开副本。首次失败的归档也在成功验证后删除。
没有修改全局环境、忽略未知条目、关闭校验或提前删除源文件。

## 边界

- 上述组合是在本机 macOS 系统 bsdtar 上验证的，不把它当作所有 GNU tar 或平台的通用参数。
- 如果备份目标要求保留资源叉、扩展属性或 ACL，应明确建模并验证这些元数据，不能直接套用内容归档策略。
- 不要无条件跳过归档中的全部 `._*` 文件；源目录可能确实存在同名文件，清单需要区分源文件与合成元数据。
- 校验失败时，停止删除。压缩包存在、压缩进程退出零都不能替代完整内容校验。

## 证据

本机 `tar --version`、`man tar`；首次归档发现源清单之外的 AppleDouble 条目，
删除计数为零；关闭元数据后的小探针通过，完整归档逐文件大小/SHA256 校验通过。
