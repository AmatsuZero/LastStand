## 现象

新跑的 x8 实验通过二进制下载和校验，写端小工程作业随后报 `ValueError: bucket belongs to another experiment`。错误出现在 S3 权限探针阶段，早于 x8 启动和编译。

## 已验证成因

这个实验把 S3 桶作为隔离单位。写端首次使用空桶时，先确认 `ListObjectsV2` 的 `KeyCount` 为 0，再用 `If-None-Match: *` 写入 `trial-probes/owner`，值为本次流水线 ID。后续读写作业的归属检查都要求这个对象返回 HTTP 200，内容与当前流水线 ID 一致。取消流水线后，远端对象归属仍然保留。

用现有读写身份分别签名 GET，两个请求都返回 HTTP 200 和上一条流水线 ID，确认这次失败发生在桶归属检查。该错误也可能由其他 GET 状态触发，排查时先查状态和合法的归属值，避免仅凭异常字符串推断。

## 有效恢复

1. 为新的流水线单独创建空桶。保留原桶及其归属标记。
2. 为写端和读端配置新桶上的既有权限。写端可 List、Get、Put，读端可 Get。以发起真实请求的身份验证新桶为空、两端读取缺失归属对象均返回 404、读端 PUT 返回 403。
3. 仅在新流水线的参数中指定新桶并打开实验开关。新流水线的写端认领该桶后，检查读端是否能读取同一批对象，并取得编译缓存命中。

SeaweedFS 4.54 的静态 `-s3.config` 可以在备份并替换配置后用 `SIGHUP` 热加载。先核对容器里实际运行的版本和上游端口，再从 API 验证新旧桶，两次读取容器启动时间可确认没有重启。

## 边界与证据

同一流水线的作业重试继续使用原流水线 ID。新建流水线会产生新 ID，需重新准备空桶。不要把新 ID 写进旧桶的归属标记来重跑，否则新实验会混入旧实验留下的 CAS 和 Action Cache 对象。

在 SeaweedFS 4.54 上复现旧桶拒绝新流水线，随后完成独立空桶预检。上线时保留了旧桶归属，热加载前后容器启动时间相同。小工程的读写探针和签名 IPA 分开判断，存储预检只证明新桶可用。
