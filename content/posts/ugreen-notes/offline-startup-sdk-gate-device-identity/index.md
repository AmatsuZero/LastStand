## 现象（symptom）

离线启动测试已能进入登录后的首页，固定响应也能通过传输层单元测试，但真机首页一直显示空设备列表。测试等待目标设备卡片超时。

解除第一层阻塞后，真实云端解析已返回一台设备，关系快照也发布成功，首页能够显示卡片；UI 测试仍找不到该卡片的业务标识。

## 已验证成因（verified cause）

第一层是请求发出之前的第三方 SDK 登录门控。首页刷新先等待 RTCX SDK 真实登录成功，再请求账号设备列表。离线测试注入的是本地占位会话，不具备该 SDK 的真实凭据，因此即使 HTTP fixture 完全正确，也没有机会接收到设备列表请求。

第二层是 fixture 混淆了不同身份字段。响应把业务设备 SN 和 RTCX `iotId` 写成同一个值，而原生设备模型明确禁止把 `iotId` 当作业务 SN。显示名称仍能渲染，但解析出的业务身份为空，依赖该身份的卡片标识和页面参数无法建立。

这两个问题发生在传输前和模型绑定后，单独验证 JSON 可以解码、URLProtocol 能返回响应，都无法覆盖它们。

## 有效恢复（effective recovery）

- 仅在内部 UI 测试构建且显式启用启动 fixture 时，让首页直接进入原有云端列表请求、解析和绑定路径，不等待真实 RTCX 登录，也不在列表成功后触发真实 SDK 设备刷新。普通构建及旧的无设备本地会话保持原流程。
- 为固定设备提供不同的业务 SN 与传输层 `iotId`；账号列表和家庭列表使用一致的映射。保留真实模型对身份的校验，不直接向 ViewModel 填入设备，也不放宽 UI 断言。
- 给 fixture 预检增加回归：任一设备响应把 `iotId` 设为业务 SN 时拒绝；保留单设备、原始业务响应和未知请求失败等现有约束。

排查时分别收集请求是否发出、云端解码数量、关系快照数量和最终控件树。控件树显示空态与显示卡片但缺少业务标识，指向不同的故障层。

## 边界（boundaries）

这是受控离线业务路径的修复，不代表真实 RTCX 登录、MQTT、视频或设备硬件功能已验收。测试记录应明确这项外部依赖边界，不能把 Mock 场景耗时直接当作真实账号线上体验。

卡片存在、卡片可点击、真实详情页加载完成和有效启动性能样本，仍是不同的验收结果。普通功能用例经过多次启动后通过，不等于已证明全新安装、无缓存、唯一启动或系统首帧采集。

未完成独立安装状态范围审计时，继续保留状态准备的拒绝条件；不要为了让性能任务变绿而跳过清理证明、删除全部 Keychain 或给缺失指标填零。

## 证据（evidence）

2026-11-12 真机复测中，原始首页启动 fixture 用例失败。只解除 SDK 门控后，原生日志记录新鲜云端关系快照含一台设备，控件树也出现该卡片，但目标业务标识仍缺失。随后读取真实模型的 SN 解析代码，确认其排除了与 `iotId` 相同的值。

新增身份预检测试在修复前有两个子用例失败，修复响应与校验后 13 项 fixture 测试通过；完整脚本测试 517 项通过，采集及状态处理的 macOS 源码测试 31 项通过。增强后的真机用例还验证卡片可点击，并等待真实 bundled RN 详情容器进入内容阶段；与原有五项本地 UI 用例合计六项通过。详情观测标记只在显式 fixture 测试模式下开放，性能事件仍由专项性能编译条件控制。

这些证据证明离线首页、真实详情导航和原有 UI 回归恢复，不证明有效 fresh-install 性能基线或每日 CI 编排已经完成。
