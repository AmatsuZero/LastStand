## 现象（symptom）

两台 macOS Runner 和一套 Docker Runner 已通过同一 NAS S3 服务共享缓存，但生产任务向下游分析任务交付的大包仍上传到 GitLab Artifacts。只修改 Runner 的 `[runners.cache.s3]`，不会改变这份交接文件的去向。

## 已验证成因（verified cause）

现有缓存和必需的任务交接使用两条独立链路：Runner 负责缓存归档的上传、恢复；分析任务通过 `needs: artifacts: true` 获取生产任务的 Artifacts。缓存后端配置不能替代项目对交接文件的上传、来源识别、下载和校验。

独立的交接语义也不要求独立部署一套存储服务。实测可以复用已有桶，用不同对象前缀分开缓存与交接文件。真正需要核对的是凭据暴露范围、对象来源和保留规则，不能仅凭桶名判断数据属于可随时淘汰的缓存。

## 有效恢复（effective recovery）

1. 先核对实际服务加载的配置、注册 ID 和 Docker 容器挂载，分别验证 macOS 主机和分析容器能访问 NAS。
2. 将大包写入独立的 `handoffs/v1/` 前缀。对象键包含项目、流水线、生产任务、完整提交和 SHA256，避免取到其他任务或重试的产物。
3. 上传后完整回读，验证大小与 SHA256，再生成小清单并移除本次 Artifacts 目录中的大包副本。原生产者副本保留。
4. GitLab 继续保存小清单和状态；消费端按清单恢复并校验大包，再进入原有分析流程。展示报告继续保留原来的 Artifacts 路径。
5. 明确交接前缀的保留期。不能把整个共享桶纳入短期缓存清理。回退传输方式后，旧 NAS 任务重试仍需保留读取权限和对象。

## 边界（boundaries）

- 匿名 HTTP 403 只能证明对象服务响应，不能证明认证读写可用。
- 已有账户可以复用，但账户权限不会因对象前缀自动收窄。向项目注入凭据会扩大其可用位置；本例只向受保护分支提供 protected、masked 变量，凭据通过进程内存和 stdin 传输，不进入仓库、命令参数或清单。
- 桶返回 `NoSuchLifecycleConfiguration` 表示当前没有该项自动过期配置，不能当成已经部署了长期保留策略；还需约束后续维护规则。
- 成功下载并校验仍不能代替解析验收。已有构建数据的重放，也不能代替代码合入后首次正式流水线的验收。
- 此方案针对下游确实需要消费的数据。发布制品和仅供展示的报告应分别遵循现有分发、留存约定。

## 证据（evidence）

同一个约 9.6 MB 的真实构建数据包，分别在两台 macOS 主机运行当前上传实现：签名 PUT、完整 GET、大小和 SHA256 验证均通过，随后 Artifacts 交付目录仅留下小清单和状态。两台 Mac 和实际分析使用的固定 Linux 镜像分别从 NAS 恢复，原分析流程均返回 `PASS`。另有回归测试确认共享桶的交接对象始终位于独立前缀。

本文省略真实用户名、主机名、内网地址、项目及任务编号、存储账户、凭据和内部镜像地址。
