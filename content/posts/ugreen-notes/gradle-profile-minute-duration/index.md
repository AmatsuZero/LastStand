一次 iOS Release 构建跑了将近 17 分钟，Gradle 日志里能看到 Kotlin/Native 的 framework 链接任务。CI 输出的耗时排行榜却由一个 55 秒的兼容性检查领跑，连链接任务的名字都找不到。

## 原因与修复

Gradle 9.4.1 的 `--profile` HTML 会把较长的耗时写成分和秒。原先的汇总脚本只匹配数字、小数点和末尾的 `s`，因此 `55.426s` 能进榜，持续十几分钟的任务则被整行跳过，脚本仍然正常退出。

修复时把时、分、秒转换成秒再排序，用跨分钟的报告做回归测试。双平台并行构建时，从每个 Gradle 进程的日志取得它自己的报告路径，并在临时工作区回收前提取数据。这样可以区分工具链预热、真机构建和模拟器构建。

## 回放与计时边界

用修正后的脚本解析同一份真机原始报告，总用时 **1018.160 秒**，其中项目配置 **14.752 秒**。原来榜上缺席的链接任务实际用了 **785.500 秒**，排在第一位。

编译任务可能并行，累计任务时长与整次构建的墙钟时间要分别记录。两个平台同时构建时，也应分别保留各自的报告，观察较晚完成的那一路。

## 链接任务里面还有哪些阶段

Gradle 把生成 Release framework 的过程记在一个 `linkPodReleaseFramework…` 任务下。要区分 Kotlin 代码生成、LLVM 优化和 Apple 链接器的用时，可以在手动诊断构建里，给 Kotlin/Native 的 Release framework 链接任务加上 `-Xprofile-phases`。测量时关闭成品 framework 缓存，为该链接任务禁用 Gradle 构建缓存和 up-to-date 跳过。依赖、工具链和已编译的 Kotlin 库仍可复用，测到的是重新链接成品的成本。

Kotlin/Native 2.4.0 为一个只有单个函数的静态 framework 也输出了约 3.7 万行计时，包含许多按文件重复的优化步骤。CI 可以把两个平台的原始输出分别保存到构建产物里，页面上只打印主要阶段。每份日志都应有编译器总耗时 `Compiler`。LLVM 的细分 pass 已经包含在上级优化阶段中，计算各阶段占比时要避免重复相加。

在一台 Apple M4 Pro 上并行重链接真实工程，两份原始日志各约 47 万行。真机和模拟器的编译器总耗时分别为 649 秒、639 秒。两边最久的都是生成目标文件（199 秒、198 秒），其次是 LLVM 模块优化（114 秒、115 秒）。消除冗余静态初始化调用也各花了 100 多秒，最终系统链接器只占 0.6 秒、0.9 秒。这组结果描述的是这次优化级别和工具链下的 Release 构建；能按相同输入复用完整的 framework 时，这些阶段才可以一起跳过。
