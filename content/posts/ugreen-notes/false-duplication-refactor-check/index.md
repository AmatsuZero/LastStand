## 现象（symptom）

一次 Python 工具链治理的设计阶段，凭「多处 HTTP 请求样板重复」这个印象，拍板了「彻底重构、抽公共层、改测试 mock 路径」，并据此规划了多个阶段。真正动手前逐文件取证，发现所谓重复几乎全是**语义各异的假重复**：强抽成统一函数会丢行为、破坏各调用方的测试 patch 点、制造一个巨型参数化函数，净效果为负。最终用户两次改口，推翻了自己此前「彻底重构」的决定。

## 已验证成因（verified cause）

把候选按维度列成表逐一比对，而不是看表面像不像：

- **HTTP 请求 8 处**：认证方式各异（Basic token / PRIVATE-TOKEN / JOB-TOKEN / 外部传入 headers）、超时各异（20/30/60/可配置）、有的带 3 次重试且防重复 POST、有的限长 5MB/8MB、有的用 `add_unredirected_header` 防重定向丢凭证、有的自定义 opener 做安全重定向。测试 patch 点也各不相同（有的 patch 模块的 `_open`，有的 patch 自定义 opener）。统一成 `http_json(auth, timeout, retry, ...)` 会同时踩中所有差异。
- **原子写入 4 处**：一处注入 `updated_at` 且 `sort_keys`，一处不注入但带 try/finally 清理临时文件，一处二进制写入且 `fchmod 0o600`，一处二进制写 `.partial` 后缀且不建目录。
- token 读取、stderr 输出、仓库根定位同样：各处绑定的变量/前缀/语义不同。

关键认知：**表面像样板 ≠ 可抽象**。只有「抽了不改任何行为」才是真重复。反过来，工程里真正已在跨脚本复用、有测试的按主题 helper（GitLab 合同层、Wiki 读写三件套、通知层、格式化层）才是复用的正确形态——它们各自封装了一类业务语义，被多个脚本 import。

## 有效恢复（effective recovery）

- 动手前对候选做逐项比对表：认证、超时、重试、限长、重定向、异常语义、测试 patch 点、编码/权限/时间戳——只有全部一致的才抽。
- 承认「剩余重复是各脚本独立演进的合理结果」，不为凑 DRY 强抽；把重构目标取消，治理价值集中到真正有收益的部分（本例是锁版本 + CI 统一调用）。
- 取证推翻自己或用户已拍板的前提时，明确声明作废、给逐项证据，让用户重新定方向，而不是带着已知错误的前提继续推进。

## 边界（boundaries）

- 这是针对「以消除重复为目标的重构」的判断方法，不是否定一切抽象；真正语义一致、已被跨脚本验证复用的模块仍应保留和归拢。
- 假重复的判定依赖逐维度取证，不能只看代码行数或 grep 命中数；取证本身有成本，但该成本远低于强抽后的回归。
- 用户重视「代码更清晰」，但接受「假重复不强抽」的结论，不会为形式上的 DRY 要求硬抽。

## 证据（evidence）

对 8 处 HTTP 调用和 4 处原子写入分别列出逐维度对照，每一处都找到至少一项不可统一的语义差异；据此判定全部不抽。验证阶段全量单测通过，且真实流水线跑通——说明「不抽」没有引入回归，而此前规划的重构若强推，会改动大量测试 patch 点并带入行为变化风险。
