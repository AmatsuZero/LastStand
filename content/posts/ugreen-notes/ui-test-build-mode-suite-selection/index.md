## 现象

同一 XCUITest target 同时包含普通启动、本地 mock 和真实账号注入用例。
关闭测试版 framework 后仍选择整个 target，依赖注入能力的用例会执行编译条件中的
`XCTFail` 分支。此时普通启动可以正常工作，整套测试却必然失败。

## 已验证成因

脚本把“会话模式”与“编译能力”混为一谈：只对本地 mock 缩小测试集合，其他模式
使用整个 target。普通二进制不含测试注入符号，也未定义对应编译宏，因此不能执行
同 target 中的注入用例。

原脚本测试用成功退出的替身替代 xcodebuild，只断言配置参数与退出码；这些测试没有
断言实际选中的 suite，无法发现选择了不兼容用例。

## 有效恢复

按两项条件明确选择 suite：

- 普通二进制或普通源码构建：仅普通启动用例。
- 测试版构建加本地会话：仅本地会话和 mock 场景用例。
- 测试版构建加真实账号会话：仅账号注入用例，并预检凭据是否存在。

用 `-only-testing:<target>/<suite>` 明确传递集合。回归执行真实根目录与宿主目录
两个 Make 入口，检查完整的 `-only-testing` 参数集合，不能只检查其中一个参数存在。

## 边界

参数回归通过只证明选择正确，不证明真机初始化、签名、账号有效或断言通过。
账号测试凭据由安全环境配置提供，不写入命令参数或笔记。

## 证据

修复前新增断言在普通二进制、普通源码及两个 Make 入口中复现选择整个 target 的失败；
修复后入口 suite 的 15 项测试通过，全套 CI 脚本 349 项测试通过。


## 关联踩坑：切换到新源码 pin 后须验证 Swift 调用签名

现象：测试版 KMP framework 已编译成功，宿主 Swift 却因新增参数报
`Missing argument for parameter`。只验证旧源码 pin 的真机结果不能证明新 pin 可用。

已验证成因：新版 Kotlin 工厂新增可空参数，即使 Kotlin 声明有默认值，生成的
Objective-C/Swift 接口仍要求 Swift 调用方显式传参；已发布二进制仍只有旧签名。
同一功能的 tracking 与 configuration 工厂可能同时变化，须检查所有调用入口。

有效恢复：在现有源码编译宏边界分别调用新旧签名；根据实现确认后传 `nil` 以保留
原有安全区回退。先对真实 Swift 调用片段执行两种 API 的编译回归，再对齐 gitlink
与子模块 HEAD，完成 framework、宿主及真机的顺序验证。

边界：编译探针仅验证调用兼容；不证明页面布局、真实账号或硬件配网成功。
本次两个工厂的源码签名均先复现编译失败、修后新旧签名均通过；同 pin 的签名真机
执行五条本地 mock 用例通过，零失败。
