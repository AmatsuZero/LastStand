## 现象（symptom）

反馈 ZIP 同时包含设备日志、录屏和内层 App 日志 ZIP。分析器能读设备明文，却找不到 App 对讲状态。手工打开内层 ZIP 可以找到启动与成功回调。

同一日志行还可能有多个时间：外层是 App 转发落盘时刻，内层是 SDK 事件时刻。按第一个时间筛选，会把延迟转发的事件推迟或筛掉。

## 已验证成因（verified cause）

旧读取器仅遍历 ZIP 第一层的日志，忽略其中的 ZIP。空事件集不能证明现场没有操作。

SDK 事件通过 App 日志设施转发，外层与内层的时间并不总相等；它们记录的是不同阶段。设备侧墙钟也可能有偏差，不能混算。

## 有效恢复（effective recovery）

递归读取内层 ZIP，保留 `app.zip!/目录/app.log` 和原始行号。所有层共享大小与成员数预算，并限制递归深度。即使不写出解压成员，也要验证路径和加密状态。

为已识别的 SDK 格式选择内层时间；App 事件保留 App 时间。窗口筛选与耗时使用同一个时间字段，输出标注时钟来源。

只配对同一文件、同一对象、同一时钟的起止事件。远端用相同请求序列关联，两端内部耗时分别计算；时钟未校准时不计算跨端单程网络延迟。

## 边界（boundaries）

- SDK 成功、远端扬声器启动、实际听到首声是不同终点。
- 日志跨度给出长耗时链路候选，不能代替运行栈采样证明 CPU 热点，也不能凭线程耗时警告认定锁竞争。
- 音频缓冲与视频同步补偿不能直接相减为实测声画偏移；实际偏移需要共同音画标记。
- 此处验证的是读取与取时恢复，不代表音频初始化故障已修复。真实包、身份、请求序列和媒体不进入公开知识库。

## 证据（evidence）

专项 24 项测试通过，覆盖嵌套成员路径/行号、共享预算、深度上限、内层异常路径拒绝、外层时间跨出窗口而内层时间仍在窗口、不同对象/文件不能配对。

真实反馈包离线重跑提取 107 条窗口内事件，同对象 SDK 调用到成功派发的耗时与人工复核一致。公开草稿仅保留数量与一致性结论，不附原始数据。

## 补充：时间字段要按日志结构定位

取同一行的最后一个时间戳仍可能误读控制消息 JSON 中的业务时间。回归样例让回包正文携带另一个时间，旧规则把正常的毫秒级往返拉长到数小时。

限定 SDK 日志头的时间位置，线程事件优先取线程标记紧邻的时间；控制消息取 SDK 包装头的时间。分段时，录音事件要求同一文件、同一线程和完整的生命周期顺序，碰到停止或重复开始时放弃该链路。控制消息按同文件、设备和请求键唯一配对，仅输出关联别名。用合成样例验证误配边界，并用原报告的真实输入离线复算，两段关键耗时与原行复核一致。
