## 现象

希望确认原生 Xcode 的内容寻址缓存（CAS）能否在两台物理 Apple silicon Mac 间复用。受控实验使用 Xcode 26.5（17F42）模拟器、一个很小的 Swift/Objective-C fixture、独立 DerivedData，以及完整还原的本地 CAS。

机器 A 本地重放 ZIP 后有 100/104 个编译缓存命中。相同 ZIP 在机器 B 的真实 Xcode 路径不同，即使用符号链接，仍为 0/104。将两台机器上的 Xcode 保持在相同物理路径的独立私有 APFS clone 中，并对齐 fixture 路径后，机器 B 冷启动仍为 0/104。

## 已验证成因

本实验中的跨机命中依赖可重现的缓存内容和受控的工具链、fixture 路径配置。仅带入 ZIP 不能让机器 B 命中，其本地 CAS 中也没有对应对象。恢复来自机器 A 的 S3 快照后，机器 B 达到 100/104 命中（96%）。

这证明的是 Xcode 的 CAS 在这组受控条件下可被跨机还原和复用，不能把 GitLab 恢复了归档与编译器实际命中混为一项结论。

## 有效恢复

将完整 CAS 快照作为待恢复的构建输入，在机器 B 上恢复后再执行相同 fixture。该实验的 ZIP 为 57,061,806 字节，上传为 0.536 秒，下载为 0.547 秒。恢复后重放得到 100/104 命中。

作为局部失效探针，仅改动一个 Objective-C 源文件中的常量，随后本地重放为 98/104 命中（94%）。该数字是远端恢复完成后的本地部分失效结果。

后续性能评估应分开记录 GitLab 恢复归档、CAS 实际命中、构建总时长和缓存传输开销。重复的稳定化计时需要包含这些开销，不能只报告命中后的编译阶段。

## 边界

- 实验没有覆盖 App 构建、Swift 命中率或一般性的构建提速。
- 此处的 Xcode 真实路径对齐是已测试配置，不是所有环境都必须遵循的通用不变量。
- APFS clone 仅用于自有临时位置的实验 A/B，对 macOS 磁盘管理没有生产建议。
- 缓存归档恢复成功不能单独证明编译器命中，须从构建输出分别确认。

## 证据

两台物理机器、相同 Xcode 版本与受控 fixture 的实际结果为：机器 A 本地 ZIP 重放 100/104，机器 B 在路径不同时为 0/104，路径对齐后的机器 B 冷启动仍为 0/104，恢复 S3 快照后为 100/104，单个 Objective-C 常量改动后的本地重放为 98/104。未记录端到端构建时长或精确编译器调用，因此本文不对它们作出结论。
