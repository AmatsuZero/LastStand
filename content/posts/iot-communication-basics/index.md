## 配网：把 Wi-Fi 告诉设备

配网的核心目的只有一个：**安全地把家庭 Wi-Fi 的 SSID 和密码告诉硬件设备**。设备出厂时并不知道家庭网络，手机作为用户侧入口，承担「转交凭据」的角色。下面是几种主流方式，从最常见到更先进。

### 1. AP 模式（热点模式）

最经典、最通用的备选方案。

1. 设备首次通电后自身创建 Wi-Fi 热点（名称常类似 `XXX-Camera_XXXX`）；
2. 手机在 Wi-Fi 列表里连上这个热点（提示「无法提供互联网访问」是正常的）；
3. App 检测到已连设备，提供界面让用户选择家庭 Wi-Fi 并输入密码；
4. App 通过这条临时本地连接把 SSID / 密码发给设备；
5. 设备关闭热点，用收到的密码去连家庭路由器，成功后配网完成。

**优点**：通用性强，几乎所有智能硬件都支持，不依赖路由器特殊功能，稳定性高。
**缺点**：用户需手动切换 Wi-Fi，过程中手机无法上网，体验不流畅。

### 2. Smart Config（一键配网）

目前体验最好的主流方式。

1. 设备通电后进入混杂模式，监听空气中所有无线数据包；
2. 用户在 App 输入家庭 Wi-Fi 密码后，手机用 **UDP 广播**将 SSID / 密码加密后，打包在**数据包的长度**里发送——像摩斯电码，通过长度变化传信息；
3. 设备虽无法解密内容，但能「听」到数据包的长度规律，从中破译出 SSID 和密码；
4. 设备主动去连家庭 Wi-Fi，并通知 App 配网成功。

**优点**：无需切换 Wi-Fi，全程在 App 内操作，体验极佳。
**缺点**：无线环境复杂（干扰多、2.4G / 5G 同名）时成功率可能降低；安全性相对 AP 模式稍低（信息已加密，但存在被嗅探的理论风险）。

### 3. 声波配网

常见于无屏幕设备（智能音箱、家电）。手机把 Wi-Fi 信息编码成高频 / 低频声波，设备用麦克风接收解码。

**优点**：不依赖无线通信协议，兼容性独特。**缺点**：对噪声敏感，传输速率慢，不适合大量数据。

### 4. 蓝牙辅助配网（BLE）

设备开启低功耗蓝牙广播，手机通过点对点蓝牙通道把凭据发给设备。

**优点**：连接稳定、不受复杂 Wi-Fi 环境干扰、安全、功耗低。**缺点**：设备需具备蓝牙模块，增加硬件成本。

### 5. 二维码配网

手机把 SSID / 密码 / 服务器地址生成二维码，设备摄像头扫描解码。

**优点**：直观快捷，可传递更丰富信息。**缺点**：需设备有摄像头，适用场景有限。

**组合策略**：实际产品往往「首选 Smart Config，失败则引导蓝牙或 AP 模式」，多模式并存以保证任何网络环境下都能配网成功。

## MQTT：物联网的发布 / 订阅总线

MQTT 是一种基于**发布 / 订阅**模式的轻量级消息传输协议，专为低带宽、高延迟或不稳定的网络设计。

把它想象成一个「邮件分发系统」：

- **发布者**：生产信息的客户端（如温度传感器）；
- **订阅者**：消费信息的客户端（如手机 App / 服务器）；
- **代理（Broker）**：MQTT 服务器核心，接收发布者消息并按主题分发给对应订阅者；
- **主题（Topic）**：类似「频道」，`home/livingroom/temperature` 这样的层级地址把发布者和订阅者关联起来。

核心特点：

- **轻量高效**：协议头最小仅 2 字节，省流量省电；
- **发布 / 订阅解耦**：发布者不知订阅者是谁，只需共同连到同一 Broker 并关注相同主题，扩展性高；
- **QoS**：QoS 0 最多一次（可能丢）、QoS 1 至少一次（可能重复）、QoS 2 确保一次（不丢不重）；
- **保持会话**：断线期间 Broker 可保留订阅与未确认消息，重连后恢复；
- **遗言（Last Will）**：客户端可设遗言消息，异常断开时 Broker 代为发布，通知其他客户端「该设备离线了」。

### MQTT 与 P2P 的关系

标准 MQTT 通信必须经过中心化的 Broker，所有客户端只与 Broker 通信，彼此不直接对话——所以**标准 MQTT 是客户端-服务器模型，不是 P2P**。

但可以在应用逻辑层用它构建 P2P 式交互：让两个设备互相订阅对方用于「收件」的主题。约定每个设备有专属收件箱 `p2p/设备ID/inbox`：

<pre class="mermaid">
flowchart LR
    A[Device_A 订阅 p2p/Device_A/inbox]
    B[Device_B 订阅 p2p/Device_B/inbox]
    A -->|发布 Hello 到 p2p/Device_B/inbox| Broker[(MQTT Broker)]
    Broker -->|路由给订阅者| B
</pre>

从设备交互逻辑看是 A 直连 B，像 P2P；从网络路径看仍经过中心 Broker。所以 **MQTT 本身不是 P2P 协议，却是构建 P2P 类应用的绝佳选择**——它顺手解决了设备发现、网络穿透、消息路由这些 P2P 里最麻烦的问题。

## P2P：摄像头与手机怎么直连

### 核心矛盾：为什么不能直接连

手机和摄像头通常位于不同局域网，各有内网 IP（如 `192.168.x.x`）。从外部（如 4G 手机）想直接访问家里摄像头，会遇到 **NAT 防火墙**：路由器只认识外出的请求，对外部未经请求的连接一概拒绝。直接连接在绝大多数家庭网络下不可行。

### 解决：云端服务器做「引路人」

P2P 的核心思想变成「找个双方都认识的朋友引荐一下」——这个朋友就是云端服务器。它**不是一直搬运数据的中转站，而是协调者**。过程分三阶段：

**阶段一：登录与注册**。摄像头联网后主动与拥有公网 IP 的云端服务器建立长连接并报到；手机 App 登录账号后也与同一服务器连接。服务器维护一张「通讯录」：谁通过哪条连接在线。

**阶段二：建立 P2P 隧道（NAT 穿透 / 打洞）**。用户在 App 点击观看时：

1. App 向云端请求连接摄像头；
2. 服务器分别告诉摄像头和手机「向对方的公网 IP:端口发一个握手包」；
3. 握手包目的不是传数据，而是「欺骗」各自路由器——当摄像头的数据包从家庭路由器出去时，路由器会记录「ID-123 主动向对方发过包，那么从对方返回的包允许通过」；手机路由器同理；
4. 两边「洞」都凿开，摄像头与 App 之间建立直接通道，后续视频流不再经过云端。

<pre class="mermaid">
graph TD
    A[手机App] -->|1. 登录并保活| C[云端服务器]
    B[智能摄像头] -->|2. 登录并保活| C
    C -->|3. 协调打洞| A
    C -->|3. 协调打洞| B
    A <-->|4. 建立直接P2P通道| B
    B -->|5. 视频数据流| A
</pre>

**阶段三：数据传输**。隧道建立后，摄像头把视频经 H.264 / H.265 编码后通过直接通道流向 App；云台转动、语音对讲等指令也经此通道反向发送。

### 为什么高效

- **低延迟**：数据直传，避免先上传云端再下载的绕路；
- **省带宽成本**：视频流量极大，若全走云端中转厂商需支付天价带宽；P2P 把流量分散到用户自己的网络；
- **高可靠**：直接连接通常比多节点中转稳定。

### 打洞失败怎么办

在多层 NAT、对称型 NAT 等复杂环境下，打洞可能失败。此时系统启用备选方案：**服务器中转**——摄像头先把视频流上传云端，App 再从云端拉取。代价是延迟更高、画质可能因省带宽被压缩、厂商成本高。主流厂商优先尝试 P2P，仅失败时自动降级到中转，对用户无感。

## 名词补充

- **混杂模式（Promiscuous Mode）**：无线网卡接收所有经过的信包而不只属于自己的，是 Smart Config 能「听」到长度规律的前提。
- **NAT / 打洞（Hole Punching）**：NAT 让内网设备共享公网 IP，也阻挡了入站连接；打洞通过双方先后向对方公网地址发包，使各自 NAT 设备「记住」对方并放行后续流量，从而建立直连。
- **QoS（服务质量）**：MQTT 的消息送达保证等级，按可靠性需求在 0 / 1 / 2 之间权衡。
- **遗言（Last Will and Testament）**：MQTT 客户端异常离线时，Broker 自动代发的通知消息，用于设备在线状态感知。
